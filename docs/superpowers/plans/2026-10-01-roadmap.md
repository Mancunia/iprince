# Roadmap: From `feat/tailwind` to Production — Master Plan

> **For agentic workers:** This is a sequencing plan, not a single implementation plan. Phases 0 and 1 are executable as written (checkbox steps). Phase 2 is split into sub-projects; each one goes through `superpowers:brainstorming` → spec in `docs/superpowers/specs/` → `superpowers:writing-plans` → `superpowers:subagent-driven-development` (or `superpowers:executing-plans`) before any code is written. Phase 3 is a launch checklist.

**Goal:** Ship iPrince Recruiting to production with the admin area, application flow, leads/contact, reviews, blog, editable site content and legal pages, styled with the delivered design system.

**Architecture:** Unchanged from the foundation and Plan 2 specs: Next 16 App Router, Supabase (Postgres + RLS, Auth, Storage), next-intl de/en, Tailwind v4 with design-system component classes, `features/<domain>/` with pure tested logic + `queries.ts` / `admin-queries.ts` / `actions.ts` / `admin-actions.ts`, public writes via service-role server actions behind validation, honeypot and rate limit.

**Tech Stack:** Next 16.3, React 19, Tailwind 4 (`@tailwindcss/postcss`), next-intl 4, Supabase via `@supabase/ssr`, zod 4, Vitest, pgTAP, Playwright, `@vercel/config`.

**Specs:** `docs/superpowers/specs/2026-09-30-foundation-design.md` (data model and security rules for every Plan 3 table), `docs/superpowers/specs/2026-09-30-plan2-admin-design.md`.

## Global Constraints

- Never push, merge to `main` or deploy without the user asking in that moment.
- Every admin server action calls `requireAdmin(locale)` (or `requireOwner(locale)`) before parsing any other input.
- Admin reads/writes use the admin's session (RLS applies). Service role only for public submissions, the cleanup job and owner-gated `auth.admin.*`.
- Every user-visible string goes into both `src/i18n/messages/de.json` and `en.json`. Translated DB content is jsonb `{de, en}` with `de` required.
- Styling: Tailwind utilities for layout, design-system classes from `src/styles/components.css`, semantic tokens (`bg-surface`, `text-fg-muted`, `bg-action`, `border-hairline`), never raw palette ramps, never StyleX.
- Logs never contain personal data.
- Next.js is v16: read `node_modules/next/dist/docs/` before using an unfamiliar API (AGENTS.md).
- `npm run check` (needs `npx supabase start`) passes before every commit; `npm run test:e2e` passes before every merge.
- Commit messages end with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`.

## Review Focus

1. **German legal pages missing at launch** (Impressum, Datenschutzerklärung): a German recruiting site without them is unlawful to operate. Gate: Phase 3 Step 1 refuses to proceed until 2d is merged.
2. **Privacy policy not stating the 24–48 h deletion of unsubmitted applications** (README, Production Supabase). Gate: 2d acceptance criterion.
3. **Public lead/contact forms abused for spam**: honeypot + `hit_rate_limit` must cover them exactly as the apply flow does. Gate: 2a spec + e2e.
4. **Markdown blog bodies rendering raw HTML**: an admin-authored post must not be able to inject script. Gate: 2c spec requires a sanitizing renderer and a unit test with `<script>` input.
5. **Personal data in leads/contact messages kept forever**: decide a retention rule during the 2a brainstorm, extending the existing cleanup cron if one is chosen.

## Phase 2: Plan 3 sub-projects

Each sub-project: new branch `feat/<name>` from `main` → brainstorm (answer the open questions below with the user) → spec `docs/superpowers/specs/YYYY-MM-DD-<name>-design.md` → plan `docs/superpowers/plans/YYYY-MM-DD-<name>.md` → execute → `npm run check` + e2e → review → merge on the user's go-ahead. Update memory (`foundation-decisions.md`) with status after each merge.

Shared patterns every spec must reuse rather than reinvent: `ActionResult` + field errors, `requireAdmin`, honeypot + `hit_rate_limit` for public forms, `localized()` for jsonb text, `revalidatePath` for admin + public pages, the admin list/detail layout of `applications`.

### 2a. Employer leads + contact messages

Tables: `employer_leads`, `contact_messages` (exist). Delivers: public employer enquiry form (company, contact, email, phone, professions multi-select from active professions, headcount, message) and contact form; admin inbox for both with status + notes; nav entry.

Open questions for the brainstorm:
- Where do the forms live (`/arbeitgeber` door page using `.door-employer`, `/kontakt`, or sections on the home page)?
- Email notification to staff on new lead/message? (needs SMTP/Resend decision; affects Phase 3)
- Retention for leads/messages (extend `/api/cron/cleanup-applications` or a sibling job)?
- Status values for `contact_messages`.

Acceptance: e2e submits both forms as anon and finds them in the admin inbox; pgTAP proves anon cannot read either table; honeypot/rate-limit unit-tested.

### 2b. Reviews

Table: `reviews` (exists). Delivers: admin CRUD + moderation (pending/approved/rejected, featured), public display (home testimonials, optionally per profession).

Open questions: are reviews only admin-entered, or can the public submit (then: moderation queue, rate limit, consent checkbox)? Show rating stars publicly?

Acceptance: only `approved` rows render publicly (pgTAP + e2e); featured ordering works.

### 2c. Blog

Tables: `blog_categories`, `blog_posts` (exist); public `blog` storage bucket. Delivers: admin category + post CRUD (markdown body de/en, cover upload, draft/published, featured), public `/blog`, `/blog/[slug]`, category filter.

Open questions: markdown editor (plain textarea + preview vs. a library)? Scheduled publishing? Per-locale slugs or one slug?

Acceptance: drafts are invisible to anon (pgTAP + e2e); markdown renderer strips `<script>`/event handlers (unit test); cover image uses `next/image`; posts have `generateMetadata` with OG image.

Status: delivered on `feat/blog` (spec `specs/2026-10-01-blog-design.md`, plan `plans/2026-10-01-blog.md`). Decisions: textarea + preview, scheduling via a future publish date (no cron), one shared slug, German fallback on `/en`.

### 2d. Site content + legal pages

Table: `site_content(key, value jsonb)` (exists). Delivers: admin editor for public copy (home hero, steps, about, footer contact details) and legal pages: **Impressum** and **Datenschutzerklärung** (de + en), linked from the footer and the cookie banner.

Open questions: structured editor per key (recommended, matching the no-JSON-tab choice for forms) vs. JSON editor from the foundation spec? Which home copy moves from `messages/*.json` into `site_content`? Who supplies the legal texts (lawyer/generator); does the privacy policy cover WhatsApp, tawk.to, CookieScript, Supabase (EU region) and Vercel?

Acceptance: privacy policy states that unsubmitted applications are deleted within 48 h; content edits appear on the public site without a deploy; missing keys fall back to defaults.

### 2e. Styling, SEO and accessibility pass (last)

Delivers: every public and admin page checked against the design system; `sitemap.ts`, `robots.ts`, per-page `generateMetadata`, `hreflang` alternates for de/en; favicon/OG from `public/logo`; WCAG 2.1 AA check (keyboard, focus, contrast, form labels/errors); Lighthouse ≥ 90 on home, apply, blog post. Include live blog posts in `sitemap.ts` (`/de/blog/<slug>`, `/en/blog/<slug>`, `lastModified` from `updated_at`).

Open questions: page list to sign off visually with the user; any pages the design system does not cover.

Carry-overs from the feat/tailwind review (the mobile header menu shipped with the layout overhaul): `(site)/not-found.tsx` with chrome and a home link (and a home link on `error.tsx`); footer column headings `h4` → `h2`; `aria-controls` only while the tawk consent panel is open; WhatsApp fallback when the tawk script is blocked; e2e for Admin → Settings (owner saves, editor gets 404).

Layout overhaul follow-ups (`feat/layout-overhaul`): upload real photos under Admin → Content → Photos; client to review the draft home-page copy (`home.features`, `home.trust`, `home.badge*`).

## Phase 3: Production launch

Prerequisites: Phase 0, 1 and 2d merged; 2a recommended (employers have no other entry point); user has provided domain and accounts.

- [ ] **Step 1:** Run `npm run check:legal` with the production `NEXT_PUBLIC_SUPABASE_URL` / `NEXT_PUBLIC_SUPABASE_ANON_KEY`; it must pass (no missing legal page, no `[PLATZHALTER` left). The gate checks the raw rows, so also open `/de/imprint` and `/de/privacy` on the preview deploy and confirm the real texts render (a row that fails its schema renders the placeholder default).
- [ ] **Step 2: tawk.to gate** (only if the owner will pick tawk.to): withdrawing consent while tawk.to is loaded must stop it (reload the page on `CookieScriptReject`; `TawkChat.tsx`), and "Enable chat" must load the widget without a reload with a real `COOKIESCRIPT_ID` (it relies on `acceptAction()` firing `CookieScriptAccept`; `consent.ts`). Otherwise leave the chat channel on WhatsApp.
- [ ] **Step 3: Supabase project** (EU region). `npx supabase link --project-ref <ref>` → `npx supabase db push`. Auth: disable sign-ups, min password 12, OTP expiry 86400 s, `refresh_token_reuse_interval` > 0, redirect URLs `https://<domain>/**` (apex + www), invite template from `supabase/templates/invite.html`, custom SMTP. Verify default grants for `anon`/`authenticated`/`service_role`. Redirect URLs must cover `https://<domain>/api/auth/confirm` (invite links).
- [ ] **Step 4: Vercel project.** Install the CLI (`npm i -g vercel`), `vercel link`, set env vars from `.env.example` for Production (`NEXT_PUBLIC_SUPABASE_URL`, `NEXT_PUBLIC_SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`, `CRON_SECRET` via `openssl rand -hex 32`, optional `COOKIESCRIPT_ID`, `TAWK_*`, `RESEND_API_KEY`, `NOTIFY_EMAIL_TO`, `NOTIFY_EMAIL_FROM` (Resend account + verified domain)). Region close to Supabase (e.g. `fra1`).
- [ ] **Step 4b:** In the CookieScript dashboard, set the privacy-policy link to `https://<domain>/de/privacy` (and `/en/privacy` for English).
- [ ] **Step 5: Bootstrap the owner** with `npm run admin:create` in a one-off shell using production env vars (never committed).
- [ ] **Step 6: Preview deploy → smoke test**: apply flow with a file upload, admin login, invite an editor end-to-end via real email, lead/contact form, blog post, chat channel switch, cookie banner gating tawk.to.
- [ ] **Step 7: Production deploy + domain** (ask the user first). Then trigger the cron by hand once with `curl -H "Authorization: Bearer $CRON_SECRET" https://<domain>/api/cron/cleanup` and check the Vercel logs; confirm the scheduled 03:00 UTC run the next day.
- [ ] **Step 8: Post-launch:** consider Vercel Pro hourly cron (`0 * * * *` in `vercel.ts`), uptime monitoring, Supabase backups/PITR.
